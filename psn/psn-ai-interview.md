## B. TEKNIS INTI POSISI

### Q4. Walk me through a RAG pipeline you built.

Saya bangun RAG untuk UU TNI, dokumen hukum Indonesia.

Pipeline-nya: dokumen PDF dan JSON di-load pakai PyPDFLoader dan JSONLoader, dipecah pakai RecursiveCharacterTextSplitter dengan chunk 1000 dan overlap 100, lalu di-embed pakai paraphrase-multilingual-MiniLM-L12-v2 dan disimpan di FAISS. Retrieval-nya saya kembangkan jadi hybrid — BM25 digabung dengan semantic search — lalu di-rerank pakai cross-encoder ms-marco-MiniLM-L-6-v2. Setelah itu baru masuk ke LLM, dengan UI yang menampilkan sumber pasalnya.

Alasan chunk 1000 dengan overlap 100: dokumen hukum punya pasal yang panjang, dan kalau chunk-nya terlalu kecil pasalnya terpotong di tengah, jadi retrieval-nya kehilangan konteks. Overlap 100 mencegah kalimat di batas chunk hilang dari kedua sisi.

Yang paling penting dari proyek ini bukan pipeline-nya. Saya mengevaluasi enam LLM dan menemukan semuanya halusinasi di atas 60 persen di baseline. Tanpa evaluasi itu saya akan menganggap sistemnya sudah bekerja.

### Q5. Kalau diminta pilih vector database, mana yang kamu pakai?

Tergantung kebutuhannya, dan saya akan jelaskan dari yang saya sudah jalankan.

**FAISS** saya pakai untuk prototyping karena in-process, tidak butuh server, dan cepat untuk eksperimen. Kelemahannya: index-nya hidup di memori satu proses, tidak ada isolasi per user, dan tidak ada backup atau operasional.

**pgvector** saya pakai di production, di Postgres lewat Supabase. Kelebihannya: vector ada di database yang sama dengan data relasional, jadi filter by user atau by dokumen bisa jadi bagian dari query yang sama, dan RLS-nya ikut jalan. Saya juga menjalankan migrasi 384 ke 1024 dimensi dengan runbook yang punya cutover gate dan rollback.

**Milvus, Weaviate, Chroma** belum pernah saya pakai. Dari yang saya baca, itu pilihan ketika skala index-nya sudah melewati satu database Postgres, atau ketika butuh fitur khusus seperti filtering skala besar dan manajemen koleksi. Untuk kebutuhan sekarang saya belum pernah sampai ke titik itu, jadi saya belum bisa bicara dari pengalaman.

Kalau untuk PSN: kalau datanya dokumen internal perusahaan, saya cenderung mulai dari yang paling sederhana dulu dan naik saat ada bukti skalanya butuh.

### Q6. How do you deploy an AI service in Docker?

Contoh paling konkret: service embedding di server saya.

Saya pakai image HuggingFace Text Embeddings Inference, versi 86-1.9, dan saya pin ke digest SHA, bukan tag latest — supaya model dan runtime-nya tidak berubah sendiri saat container di-restart. Modelnya BAAI/bge-m3, 1024 dimensi, dan environment-nya menerima `EMBEDDING_MODEL_REVISION` yang wajib diisi commit SHA immutable.

Sisi container: GPU reservation untuk satu device NVIDIA, memory limit 8GB, CPU 4 core, `cap_drop: ALL`, `no-new-privileges`, tmpfs untuk `/tmp`, healthcheck ke endpoint `/health` dengan start period 120 detik karena loading model memang lama, dan logging di-cap 20MB x 5 file.

Port-nya bind ke 127.0.0.1, jadi tidak terekspos langsung. Akses dari luar lewat Cloudflare Tunnel ke Nginx, dan Nginx yang mengatur routing per subdomain dan rate limiting.

Tiga hal yang saya anggap paling penting dari setup ini: **pin versi model immutable**, **healthcheck dengan start period yang realistis**, dan **jangan publish port container langsung ke publik**.

### Q7. How do you evaluate an LLM system?

Tiga tahap, dan hasilnya berubah di tiap tahap.

**Tahap baseline:** enam model, semua halusinasi di atas 60 persen. Artinya tidak ada yang layak dipakai apa adanya.

**Setelah fine-tune QLoRA:** ROUGE-1 naik sekitar 30 poin dan halusinasi turun. SeaLion paling unggul di penilaian human-judge, SahabatAI halusinasi paling rendah di 45,70 persen.

**Setelah fine-tune plus RAG:** akurasi faktual naik dan halusinasi turun sekitar 10 poin lagi — Llama 3.1 jadi 46,74 persen. Tapi ROUGE dan F1 justru turun.

Trade-off terakhir itu yang paling penting dan sering terlewat. RAG membuat jawaban lebih benar tapi lebih pendek dan kurang mengalir, karena model mengutip dokumen ketimbang menyusun kalimat sendiri. Metrik otomatis menghukum itu meski secara faktual lebih baik. Untuk chatbot hukum, grounding harus menang, jadi saya pilih yang faktual benar.

Saya pakai LLM-as-judge, ROUGE, dan BERTScore, plus tracking eksperimen di W&B.

### Q8. Kalau kamu harus membangun LLM agent untuk monitoring jaringan satelit, bagaimana pendekatanmu?

> ⚠️ **Ini pertanyaan paling penting di wawancara ini.** Agent muncul di **3 poin requirement** (JD#3, Req#4, Req#5) — gap terbesarmu. Hafal jawaban ini sampai mengalir.

Saya belum pernah membangun agent, jadi saya jawab dari yang saya sudah bangun dan apa yang beda.

Yang saya sudah bangun: pipeline di mana pertanyaan user di-embed, dokumen relevan diambil, di-rerank, baru dikirim ke LLM dengan konteksnya. Satu kali jalan, tidak ada loop. Langkahnya saya yang tentukan.

Agent menambah tiga hal. Pertama, **tool calling** — modelnya yang memutuskan mau panggil apa, bukan pipeline yang hardcoded. Untuk monitoring satelit ini berarti tool untuk ambil data telemetri, hitung agregat, dan render chart. Kedua, **loop** — model bisa mengecek hasil tool-nya, dan kalau datanya kurang, dia panggil tool lain. Ketiga, **state** — supaya percakapan multi-langkah tidak kehilangan konteks.

Yang tidak berubah: retrieval, evaluasi, dan reliability-nya. Worker queue, retry, dead-letter yang saya bangun untuk indexing tetap dibutuhkan, karena tool call yang gagal itu kondisi normal, bukan pengecualian.

Satu hal yang saya pahami tentang konsekuensinya: kalau langkahnya ditentukan model, **debug-nya jauh lebih sulit**. Di pipeline saya, kalau hasilnya salah, saya bisa lihat dokumen mana yang diambil. Di agent, saya juga harus bisa melihat kenapa dia memilih tool itu — jadi tool-nya harus bisa diperiksa hasilnya, dan jumlah langkahnya harus dibatasi.

Kalau saya dikasih tugas itu, saya akan mulai dari satu tool yang paling sering dipakai operator dulu — misalnya query history telemetri satu kanal — dan mengukur berapa langkah yang benar-benar tersimpan. Agent tanpa tool yang berguna cuma tambah lapisan yang tidak bisa di-debug.

### Q8b. Apa bedanya tool calling dengan API integration biasa?

Di integrasi API biasa, **saya** yang menentukan fungsi mana yang dipanggil dan kapan. Di tool calling, **model** yang menentukan.

Saya sudah banyak melakukan yang pertama: `api_client.py` di LawBot POST ke endpoint `/predict`, service embedding saya punya endpoint sendiri dengan API key, EZVIZ Open Platform untuk sinkronisasi device, Google Drive OAuth untuk arsip. Semua itu alurnya saya tentukan di kode.

Yang belum saya lakukan adalah yang kedua. Dan bedanya bukan cuma siapa yang memutuskan — bedanya juga **kontraknya**. Di integrasi biasa, saya tahu parameternya karena saya yang menulis pemanggilnya. Di tool calling, model yang membaca schema-nya, jadi type hint dan docstring fungsinya menjadi bagian dari kontrak. Kalau deskripsinya kabur, modelnya memanggil tool yang salah atau tidak memanggil sama sekali.

### Q9. Kenapa RAG dan bukan fine-tuning? Kapan pakai yang mana?

Dua-duanya saya kerjakan, jadi saya bisa bandingkan dari hasil.

**Fine-tuning** bagus ketika masalahnya **gaya dan format** — model perlu berbicara dengan terminologi domain, atau perlu mengikuti struktur jawaban tertentu. Di proyek saya, fine-tune QLoRA menaikkan ROUGE dan menurunkan halusinasi, artinya modelnya belajar terminologi dan cara menjawab.

**RAG** bagus ketika masalahnya **pengetahuan yang berubah**. Dokumen hukum, peraturan, data operasional — ini berubah terus dan tidak mungkin di-retrain setiap perubahan.

Tapi dari hasil eksperimen saya, **kombinasi keduanya paling baik**, dan itu kesimpulan laporan saya. Fine-tune membuat modelnya berbicara dengan benar, RAG membuat faktanya benar. Kalau harus pilih satu karena keterbatasan waktu atau compute: mulai dari RAG dulu, karena bisa diperbaiki tanpa training ulang, dan kegagalannya bisa dilacak — kamu bisa lihat dokumen mana yang diambil.

Untuk PSN, dokumen internal perusahaan dan data telemetri keduanya berubah. Jadi default-nya RAG.

### Q10. Bagaimana kamu mengukur apakah sebuah AI system layak dipakai?

Saya bedakan dua hal: apakah modelnya benar, dan apakah sistemnya berguna.

Untuk kebenaran, metrik yang saya pakai di LawBot — halusinasi, ROUGE, LLM-as-judge. Waktu baseline, halusinasi di atas 60 persen, angka itu yang memberi tahu saya sistemnya belum layak, meskipun secara demo terlihat mengesankan.

Untuk kegunaan, saya ukur waktu dan langkah yang tersimpan. Waktu magang di PLN, salah satu pekerjaan saya memotong waktu pipeline dari lebih dari satu jam jadi 28 detik. Tidak ada yang bertanya tentang modelnya. Yang mereka rasakan adalah 28 detik itu.

Jadi ukurannya dua-duanya: metrik kualitas model, dan satu angka yang dirasakan user. Kalau cuma punya yang pertama, kamu membuat sesuatu yang bagus secara teknis tapi tidak dipakai.

### Q14. Bagaimana kamu menangani kegagalan provider atau API?

Yang menurut saya keputusan desain paling penting di worker itu: **candidate generation lalu atomic activation**. Artinya kalau proses embedding gagal di tengah, index yang lama tetap hidup. Saya tidak pernah menghapus chunk aktif sebelum yang baru selesai dibangun. Dengan desain lama, kegagalan provider bisa menghapus index terakhir yang valid, dan itu jauh lebih buruk daripada job yang gagal.

Selain itu ada validasi model immutable dan enforcement 1024 dimensi, supaya tidak ada konversi diam-diam yang menghasilkan vektor tidak kompatibel.

## D. SITUASIONAL TEKNIS

### Q16. Data telemetri satelit datang dengan anomaly. Bagaimana kamu deteksinya?

Pertama, saya perlu tahu anomaly-nya seperti apa, karena itu menentukan pendekatannya. Ada dua kelas.

Kalau anomaly-nya **sudah pernah terjadi dan punya label**, ini masalah supervised. Saya akan mulai dengan baseline sederhana yang bisa saya pertanggungjawabkan — misalnya threshold per kanal yang diturunkan dari distribusi historisnya, bukan angka yang diketik manual. Lalu model yang lebih kompleks hanya kalau baseline-nya terbukti tidak cukup.

Kalau anomaly-nya **belum pernah terjadi** atau terlalu jarang untuk dilabeli, ini masalah unsupervised atau zero-shot. Di PLN saya pakai pendekatan zero-shot dengan foundation model time series. Untuk domain satelit, satu masalah yang khas adalah **seasonality orbital** — data berulang mengikuti posisi satelit, dan anomaly asli harus dibedakan dari pola normal yang berulang. Itu biasanya perlu dekomposisi dulu sebelum apapun.

Dan apapun metode yang dipakai, saya akan tanya: untuk apa deteksinya dipakai? Kalau output-nya alert untuk operator, false positive lebih mahal daripada false negative dalam jangka panjang, karena operator berhenti percaya setelah alert ketiga yang salah.

### Q17. Bagaimana kamu menangani data yang confidential?

Di LawBot juga ada konteksnya, meskipun dokumennya publik. Tapi saya bisa jelaskan dari sisi deployment.

Untuk dokumen yang tidak boleh keluar, hal pertama yang saya putuskan adalah **di mana inferensinya jalan**. Kalau harus benar-benar on-premise, berarti butuh model yang jalan lokal, bukan API pihak ketiga. Saya sudah menjalankan model 7B secara lokal dengan 4-bit quantization, dan menjalankan embedding service sendiri di Docker. Jadi jalur itu memang bisa.

Kedua, **aksesnya**. Kalau pakai vector database internal, retrieval harus difilter per user atau per role, dan filternya harus di level database — bukan di level aplikasi — supaya tidak bisa dilewati dengan memodifikasi request.

Ketiga, **logging**. Kalau prompt dan output dilog sembarangan, dokumen confidential tetap bisa bocor lewat log, meskipun modelnya jalan lokal.

### Q18. Kalau model di production mulai memberi jawaban buruk, apa yang kamu lakukan?

Saya cek urutannya dari yang paling murah diperiksa.

Pertama, **datanya berubah atau tidak**. Kalau ada dokumen baru masuk, atau format dokumennya berubah, chunking-nya bisa jadi tidak lagi sesuai dan retrieval-nya rusak. Ini paling sering, dan termurah diperbaiki.

Kedua, **retrieval-nya**. Saya akan cek dokumen apa yang diambil untuk pertanyaan yang gagal. Kalau dokumennya benar tapi jawabannya salah, masalahnya di model. Kalau dokumennya salah, modelnya tidak pernah punya kesempatan.

Ketiga, **prompt atau versinya**. Kalau saya pin model ke revisi immutable, perubahan tak terduga dari sisi provider harusnya tidak terjadi. Kalau tetap berubah, berarti asumsinya salah dan saya harus tahu kenapa.

Keempat, baru **modelnya**. Dan kalau harus rollback, saya punya jalur rollback karena index lama tidak dihapus sebelum index baru selesai dibangun.

Urutan itu penting karena kalau langsung menyalahkan model, kamu bisa menghabiskan seminggu mengganti model untuk masalah yang sumbernya di chunking.

### Q22c. Bagaimana kamu troubleshoot inference yang lambat? *(JD #9)*

Saya telusuri dari yang paling mungkin dan paling murah diperiksa.

**Kedua, lihat konkurensinya.** Kalau lambat muncul hanya waktu ada beberapa request bersamaan, masalahnya bukan modelnya tapi antriannya. Di service embedding saya, `MAX_CONCURRENT_REQUESTS` saya set ke 2 karena GPU-nya 8GB — kalau dinaikkan, VRAM habis dan justru lebih lambat.

**Ketiga, lihat inputnya.** Di TEI saya pasang `AUTO_TRUNCATE` dan `MAX_BATCH_TOKENS=4096`. Kalau tidak, satu dokumen yang sangat panjang bisa memonopoli satu batch dan membuat request lain menunggu.

**Keempat, baru lihat modelnya** — apakah kuantisasinya sudah tepat, apakah ada model yang lebih kecil yang cukup untuk tugasnya.

Yang saya belum pernah lakukan: tuning di level hardware, seperti kernel CUDA atau pemilihan dtype per layer. Yang saya lakukan adalah **konfigurasi runtime dan alokasi memori** — itu level yang saya pegang.

# 6. YANG HARUS DAN TIDAK BOLEH KAMU KATAKAN

## Boleh diklaim (ada bukti)
- RAG end-to-end: dokumen → chunking 1000/100 → embedding → FAISS/pgvector → hybrid BM25+semantic → cross-encoder reranking → LLM → UI dengan sitasi
- Evaluasi 6 LLM: halusinasi, ROUGE, BERTScore, LLM-as-judge, W&B
- QLoRA 4-bit via Unsloth, adapter ~38 MB
- Docker production: 7 service, Nginx reverse proxy, Cloudflare Tunnel, worker terpisah, healthcheck
- **Self-host HuggingFace TEI di GPU** (image version di-pin + digest, model BAAI/bge-m3 1024-dim, RTX 3050) ← **ini memenuhi Req#11 dan Req#12**
- pgvector di Postgres, migrasi 384→1024 dengan cutover gate + verification SQL + rollback runbook
- Worker queue: PGMQ, retry full-jitter, Retry-After, DLQ, candidate generation → atomic activation
- **Monitoring produksi**: frame-heartbeat, watchdog no-segment, disk watermark, worker heartbeat, reconciliation, health & metrics endpoint ← **ini memenuhi JD#7**
- Computer vision: YOLO detection + InsightFace/ResNet embedding + similarity search, 666 gambar, 94%
- Time series: RUL prediction, Cronos zero-shot, backend PostgreSQL
- Integrasi API eksternal: FastAPI, EZVIZ Open Platform, Google Drive OAuth, DeepSeek API, Telegram webhook ← **sebagian JD#4, bukan function calling**

- ❌ **Tool calling / function calling** → sebut integrasi API eksternal sebagai yang terdekat, dan jelaskan bedanya (model yang memutuskan vs kamu yang memutuskan)

- ❌ Pengalaman domain satelit → bilang belum, sebut PLN time series sebagai yang terdekat
- ❌ "Ahli" / "expert" di LLM → pakai "saya sudah mengerjakan" bukan "saya ahli"
